3. Auditoría de Seguridad y Protección de Datos (OWASP)

Para que una plataforma que gestiona datos personales y pagos sea jurídicamente sólida y técnicamente inviolable, debe cumplir con las directrices internacionales del OWASP Top 10 y la legislación local de protección de datos (Ley Nacional N° 25.326).

A. Prevención de Ataques de Fuerza Bruta (Brute-Force Protection)

Riesgo actual: Cualquier atacante con un script automatizado podría enviar miles de peticiones por segundo al endpoint /api/auth/login probando combinaciones de contraseñas.

Medida requerida: Implementar Rate Limiting en el backend mediante Bucket4j o un filtro de Spring Security. Si una dirección IP o cuenta falla 5 veces consecutivas en menos de 2 minutos, se le impone un bloqueo temporal de 15 minutos.

B. Criptografía y Almacenamiento Seguro de Contraseñas

Auditoría: Verificar que todas las contraseñas persistidas en la tabla usuarios se encuentren cifradas con el algoritmo BCrypt (strength 10 u 11) con sal (*salt*) criptográfica única generada por usuario. Nunca se debe almacenar ni transmitir contraseñas en texto plano ni con algoritmos obsoletos (MD5, SHA-1).

C. Seguridad de Tokens de Sesión (JWT)

Buenas prácticas de arquitectura: Actualmente el token JWT reside en localStorage del navegador. Para alcanzar el estándar bancario o de salud:

  • Establecer una vida útil corta para el Access Token (ej. 15 a 30 minutos).
  • Implementar Refresh Token almacenado en una Cookie HttpOnly, Secure y SameSite=Strict, impidiendo que cualquier script malicioso (Cross-Site Scripting / XSS) pueda acceder al token de autenticación.

D. Sanitización e Inyección SQL

Diagnóstico positivo: Al utilizar Spring Data JPA / Hibernate con mapeo relacional de entidades y consultas tipadas (JPQL / Criteria), el sistema está protegido por defecto contra inyecciones SQL tradicionales. No obstante, se debe mantener la regla estricta de no concatenar cadenas directas en consultas nativas.

4. Base de Datos e Infraestructura Productiva

Peligro crítico: Desactivar Hibernate ddl-auto=update en producción.
En el archivo application.properties actualmente figura spring.jpa.hibernate.ddl-auto=update. En un entorno de producción con datos reales de clientes, esta configuración es peligrosa porque una modificación accidental en una entidad Java puede alterar tablas en vivo, renombrar columnas o causar pérdida de datos.

Plan de migración segura de Base de Datos:

  1. Fijar spring.jpa.hibernate.ddl-auto=validate en el perfil de producción.
  2. Incorporar Flyway o Liquibase para que todas las modificaciones de esquema (tablas, índices, columnas) se ejecuten mediante scripts SQL versionados y auditables (ej. V1__crear_tablas_iniciales.sql).

Estrategia de Backups Automatizados (Regla 3-2-1):

  • Frecuencia: Volcado diario automático (mysqldump) programado a las 03:00 AM mediante tarea Cron.
  • Cifrado y Almacenamiento: Archivos comprimidos (.sql.gz) cifrados con GPG y sincronizados a un almacenamiento remoto seguro (AWS S3, Google Cloud Storage o servidor de contingencia).
  • Retención: Mantener backups diarios por 30 días y mensuales por 1 año.

5. Estrategia de Despliegue y DevOps

Para evitar el clásico problema de "en mi máquina funciona" y asegurar alta disponibilidad, el despliegue se debe estructurar en contenedores independientes orquestados por Docker Compose:
